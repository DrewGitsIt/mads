Git routes: from socket starvation to cached git state

Phase A and Phase B, merged together · measured 2026-11-21/22 with the local perf harness on real-git clones shaped like the live heavy session (908 files in 309 directories, 11 checkouts of one repo) · harness: docs/PERF-HARNESS-PLAN.md (“Git routes”) · design: docs/GIT-STATE-DESIGN.md

The work in brief

After the event bus stopped replaying, the slow git routes were what starved Chromium’s 6 sockets per origin. Opening or switching a session fired GET /repos (8–25 s), GET /changeset twice (3.6–6.7 s each) and POST /worktree/refresh (3–17 s). Nothing was ever cancelled, so leaving a session left them holding sockets. The biggest single cost was one git rev-parse --show-toplevel per directory in a session’s file ledger: 1,500–2,400 serial git calls per window.

Phase A (request hygiene): requests are cancelled when a view goes away, and a cancel kills the git work too. The rail and Changes tab share one changeset request; Chromium had been serialising the two identical GETs. Refresh is single-flight, skips repeat focuses, and is handed to the session process. API responses are no-store, and repo roots are found by walking the filesystem instead of spawning git. Phase B (git state served from the Router): the Router keeps each session’s branch facts, changeset and counts, recomputes them in the background when files change, a turn ends or a ref moves, and announces fresh state with session.git_state_updated. GET answers from memory in milliseconds, and a small “updating” mark shows while a recompute runs.

How a session switch works: main vs A vs B

main

switch: the views mount and fire their reads
↓
/repos: ~15–30 serial git calls per repo, plus one rev-parse per ledger directory
↓
/changeset × 2 (rail and tab): add -A, 2 diffs, status, per-file calls; Chromium queues the duplicate
↓
/worktree/refresh on every switch and every focus
↓
switch again: the old requests keep their sockets until git finishes (never aborted)

A: request hygiene

leaving a view aborts its requests; the server kills that git
↓
one shared changeset request; no-store ends the browser queueing
↓
refresh: single-flight, a 30 s focus skip, handed to the session’s own coalesced recount
↓
repo roots by filesystem walk (Push preview 98 → 16 git calls)
↓
but each read still waits for git: 1–6 s

B: Router-held git state

the Router keeps repos, changeset and counts per session; active and recently viewed sessions stay warm
↓
triggers (file changed, turn end, commit, ref moved) → background recompute, single-flight, the shown session first
↓
GET answers from memory: 2–3 ms; cold → an empty “updating” state
↓
session.git_state_updated → the window refetches only what changed; the “updating” mark clears
↓
commit lookups batched: 4–8 git calls per repo instead of 3 per commit
↓
actions (Commit, Land, Push, previews) still compute fresh

What changed after review, and what B still costs

  • Opening the Changes tab is back to A’s speed (0.07 s). Its earlier ~1 s was the background change-set build’s commit lookup (3 git calls per recorded commit), now batched.
  • Outside edits show on focus in about 2 s (0.41 s settled in this scenario). On main and A they appear only when the session is reopened.
  • Focus settles instantly. When the cached change set is older than 30 s, focus starts a background rebuild (about 50 git calls on an idle focus) so outside edits are caught. A cheaper probe gate was measured and rejected: it saved CPU you don’t notice and added complexity.
  • Background cost: the Router warms active sessions, so its CPU runs higher in some scenarios, and Push/Land may be slightly slower under load (344→419 ms, within noise).
  • Durable events: about 1–3 session.git_state_updated rows per action, at most ~12 a minute under continuous writes.

Correctness: checks f (converges to a fresh compute), g (the “updating” mark appears and clears), h (Commit, Land, Push dialogs act on fresh state) and i (outside edits, including re-edits of already-modified files) pass.
