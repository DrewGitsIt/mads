Chat stream: per-update cost no longer grows with the conversation

Fix A and fix B, stacked · measured 2026-11-24 with the local perf harness (make ui-perf SCENARIOS=chat), Chromium, N=3 per build, a 500-turn conversation (4,507 rows) calibrated against a real transcript · findings: docs/CHAT-STREAM-PER-BATCH-COST.md · harness: tools/perf/docs/PLAN.md (“Chat stream”)

The work in brief

The mads-mobile spike found that every streamed text update made the chat view redo work for every message loaded, not just the growing reply. On the Mac, with a long conversation fully loaded, the main thread was saturated while a reply streamed and frames ran at about 20 fps; on the phone it was 7 fps.

Fix A (cheap, local): each timestamp is formatted once per message instead of on every render; the quiet-check glide tracks the stream's height with a ResizeObserver instead of forcing layout on every commit; the reducer keeps recently written rows in a small layer, so a text update copies a few rows instead of all 4,500. Fix B (memoization): everything the view derives from the rows (joined bubbles, entries, items, per-call permission lists) keeps its identity while its rows are unchanged; each item renders through a memoized component that is handed only what it uses; ConversationTab passes stable callbacks. A text update now re-renders only the live reply.

What review changed, and what's left

  • The harness itself was reviewed first and fixed before any comparison: the text check now compares the streamed render (it used to read the screen after the stored copy replaced it), a run fails if the conversation didn't fully load, the full-size cost is measured below saturation (15/s), and update arrival is stamped at the proxy. Injected dropped, doubled and swapped updates are caught.
  • Fix A review: no bugs (old vs new reducer run side by side over 120,000 random steps: identical). Follow-ups landed: a test for the layer order, a non-copying tool lookup for the dock, cache reset on a time-zone change, a border-box observer.
  • Fix B review: one stale render found and fixed (Commit/Land card stamps didn't re-label at midnight); handler ref moved out of render; the comparator's rule documented.
  • Still left: layout + paint ≈ 12 ms per update at 4,500 rows, unchanged by A or B; ChatRenderer's own pass over every row is cheap but still linear. The next lever is content-visibility or rendering a window of turns — needed on the phone regardless (650 MB at 500 turns).

Correctness on every repetition: the loaded size, the wire carried the whole stored reply, the streamed render was whole and in order (and still is after the merge), stick-to-bottom held. vitest 4,352 · make ui-smoke 104/104. main and A figures come from one paired run (20261124-193131); A+B from a paired run against A (20261124-200725), where A measured within 3% of its first run.
