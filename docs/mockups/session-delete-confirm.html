Deleting a session — move the warning from the server to the dialog

Today the dialog is identical no matter what you are deleting, and the thing that actually knows better — the server — answers a confirmed delete with 409. The refusal lands as a raw-string toast at the bottom of the conversation pane, nowhere near the rail you clicked in, and the card just stays. So: drop the 409, and make the dialog say what deleting this particular session will cost. The dialog still always appears — deletion is irreversible — but it stops being the same dialog every time.

today One dialog for every session and then a 409

what you see
Delete this session?
Deleting permanently removes this session, its tasks, file-change history, and commit records. Provider transcripts and the event log survive. This can't be undone.

It doesn't know which session it is. SessionDeleteConfirmDialogProps is { open, onConfirm, onCancel } — no session, no name, no state.

what happens next, if the session is live
1You confirm. The dialog closes.
2handleDeleteSession returns 409 — either Activity == active or the supervisor still tracks a child.
3reportActionError sets a Toast reading router request failed: 409 delete session: session is active; close it before deleting.
4That Toast is position: relative — in flow, last child of <main>, i.e. the bottom of the conversation pane. It does not float, does not auto-dismiss, and is not where you were looking.
5The card is still in the rail. It reads as nothing happening.

proposed Four states, one dialog warning proportional to what is actually running

Everything below is already on the session record — activity, agent_state (state, label, since) and the rail's own open-task breakdown. The dialog just has to be handed the session instead of a bare open flag.

1 · quiet — sleeping, nothing running
Delete “Ollama parallel inference tuning”?
Sleeping · nothing running
last activity 3 days ago
Removes its tasks, file-change history and commit records.
Provider transcripts and the event log survive. This can't be undone.

Today's dialog, plus a name and a one-line state. The quiet case should stay boring.

2 · open — a child process exists, agent idle
Delete “Fix 5 MADS UI issues”?
Open · waiting on you
Deleting closes it first.
Removes its tasks, file-change history and commit records.
Provider transcripts and the event log survive. This can't be undone.

This is the case that 409s today. The child is terminated as part of the delete, and the button says so rather than the server refusing.

3 · working — mid-turn right now
Delete “Session status sidebar UX”?
Working right now — this will interrupt it
Running bash · Query data service tasks · 14s
Removes its tasks, file-change history and commit records. The turn in flight is lost.
Provider transcripts and the event log survive. This can't be undone.

The live label is the one the status line already renders, so the dialog and the card never disagree about what the agent is doing.

4 · working with a pipeline running
Delete “Monitor event-driven redesign”?
Working, and running a pipeline
Running bash · go test ./services/… · 2m
12 tasks · 1 running · 4 ready · 1 blocked
Removes 12 tasks including the one in flight, plus its file-change history and commit records.
Provider transcripts and the event log survive. This can't be undone.

The worst case gets the loudest panel and a count, because "12 tasks" is the number that should stop your hand — not the word "permanently".

A running task count is additive — it escalates the panel to the warn tone and adds a line, in any of the three states above.

Precedence is working › open › quiet, the same order the rail's status line already uses, so a card that says "working" can never open a dialog that says "sleeping".

The button carries the verb. The three labels differ because the consequences differ, and the button is the last thing read before the click. "Delete" that silently also kills a running agent is the lie worth removing.

server Dropping the gate

handleDeleteSession (services/router/internal/api/sessions.go:378) has two refusals. Both become a terminate-then-delete.

TodayProposed
Activity == active → 409 "session is active; close it before deleting" terminate, then delete
sup.SessionAddr(id) tracked → 409 "session has a running child; close it before deleting" terminate, then delete

The terminate already exists and is already safe in every state. It is the same TerminateSession the rail's close button calls, which SessionRail.tsx documents as safe to call whether or not a child is live — it kills a live child, or reconciles an already-inactive record as a no-op. That is exactly the property a delete needs, and it is the reason the record's activity flag is the wrong thing to gate on: it can drift from the real child state, so today a session whose record says active but whose child is long gone cannot be deleted at all.

Delete stays failable, just not refusable. If the terminate itself errors the delete should still report it — and that report needs to reach the rail, which is the last open question here: Toast is documented as "presentational only — no queue/provider yet", and it renders in <main>. Either it gets a portal/provider, or the rail grows its own inline error affordance on the row. Worth settling separately from this change, but not worth forgetting.
