The widget kit (v1 = 4 archetypes): select-menu (agent/model), info-panel (context/cost, read-only), form (settings like theme), confirm (destructive like clear). Each command's manifest entry names its archetype + data source + completion. New commands are data, not new components.

Framework Manifest-driven, mads-authored per provider

Reality check: today's harnesses don't expose their slash commands as structured, renderable data. So the manifest is authored in the mads provider adapter (per provider, community-extensible), not fetched from the live harness. "If the provider has /theme" means "if this provider's adapter declares it." Runtime discovery is the aspiration, not the v1 mechanism.

A manifest entry carries enough to drive a surface AND its effect:
{ name: "context",  widget: "info-panel",  source: "session.usage",
  exec: "mads-handled",  owner: "mads",  lifecycle: "pinned" }
{ name: "agent",    widget: "select-menu", source: "registry.agents",
  exec: "mads-handled",  owner: "mads",  lifecycle: "transient" }
{ name: "clear",    widget: "confirm",     source: null,
  exec: "passthrough",   owner: "provider", lifecycle: "transient" }
{ name: "vim",      widget: null,          source: null,
  exec: "terminal-only", owner: "provider", lifecycle: null }

Collision rule: when a provider command overlaps something mads already owns (provider /model vs. mads' session model picker), owner: "mads" shadows the provider entry — one /model, mads' version. Transcript rule: command cards are UI chrome, never persisted as messages — which also sidesteps the normalize-then-reject flash that raw /context hits today.
