Event bus: from replay-on-connect to live-only

Branch event-bus-live-fixes · measured 2026-11-21 with the local perf harness (300k-event log, Chromium, git delays off unless noted) · full conditions and tables in tools/perf/docs/EVENT-BUS-RESULTS.md

The work in brief

Every mads window shares one SSE connection to GET /events (the “bus”). On main that bus resent the event log from seq 0 whenever it (re)connected: on load, on every session switch (a bug), when a view added a new event type (e.g. opening a delegate), and when you came back to the Sessions tab. With a ~300k-event log that is 30–330 MB per action, seconds of main-thread work to dispatch it, and one of Chromium’s 6 sockets held while small requests queue behind it.

The new bus is live-only: it reads the log head, connects from there, and never resends history. Views load their state over REST, after a ready barrier that makes the order 100% safe. Approvals, queue, pipeline-running and provisioning, which only arrived by replay, now have REST snapshots. Reconnects back off at most 2 s (2 × the measured restart time) and wake immediately on online/visibility.

Old design vs new design

main: replay on every (re)connect

loadswitch*new typetab return
the bus (re)connects
↓
cursor = min over types; a type never received counts as 0 → since = 0
↓
Data Service streams the whole log for every subscribed type: 31–328 MB, 50k–165k frames
↓
renderer parses and dispatches every frame (up to ~20 s main thread); already-seen ones are dropped after download
↓
views also do their own REST reads, which queue behind the busy sockets (6 per origin)

* a switch reconnected even with no new types: the bus compared against current subscribers, not what the open connection carried. Leaving the Sessions tab also threw the cursors away.

new: live-only with a ready barrier

GET /events/head → H (once per window; ~1–3 ms)
↓
connect since = H; cursor = H → eventsReady() resolves
↓
each view: subscribe → await ready → REST snapshot → merge (live wins / dedupe by seq) — nothing between H and the snapshot can be lost
↓
only new events flow; a new type, a drop, or a tab return resumes from the cursor, never from 0
↓
down? backoff ≤ 2 s, instant retry on online/visible; head 404 → “Restart mads” banner; Router logs Data outages

Every one of ~38 subscriber files is held to this by a guard test; 33 mount readers are covered by a barrier table test.

What is left: socket starvation from slow git routes

With the git routes mocked at their live speeds (repos 10 s, changeset 6 s, worktree/refresh 16 s), a session switch settles in the same time on both builds (14.8 s → 15.1 s). With the replay gone, those slow requests go out sooner and small requests wait behind them, so total queued time rises (84 s → 140 s across a switch) while main-thread work drops (1.5 s → 0.6 s). The bus is no longer the bottleneck; the git routes are. That is the next piece of work (timeouts, cancellation, request ordering, faster routes).
