Session rail — pass 5: three dimensions, three homes

Pass 4's Option A is settled below with one change (a warning triangle for “needs you”). The rest of this page answers the harder question: three things you want the indicator to carry, and whether it can. It can — but not all in the same place. They are three different kinds of fact, and the design works by sorting them by kind rather than stacking them on one glyph.

Updated 2026-10-09. §(b) is parked — a visible countdown turns a cost hint into a deadline, and nobody should be hurrying to type before a timer runs out. The section is kept rather than deleted: the findings are the groundwork for a later conversation about what mads can do to reduce token cost, where the right answer is probably to act on the cache rather than to report it. §(d) is new — the checkmark has been reassigned to Set aside, so the Done status needs a different mark.

The shape of the problem read this first three wants · three kinds of fact · three homes

a What it's doing

A state machine — mutually exclusive, changes on events, demands action or doesn't.

Home: the mark and the label. Already correct. Nothing in this pass changes it except the triangle.

b Cache warmth

A decaying number — continuous, driven by the clock alone, and only legible once the session is at rest. It never demands action; it prices one.

Home: the time stamp. Warmth is a function of time and nothing else, so it is drawn on the field that already means “when”, not on the one that means “what”.

c Whether you care

A decision you make — not an observation about the session at all. The only one of the three the session itself cannot answer.

Home: list membership. It belongs to the fold, not the card: “where is this in my list”, not “what is this doing”.

Why this is the whole answer. Your worry — can one indicator hold all of it — is well founded, and it would not. A 10px mark can carry one categorical fact legibly, two with difficulty, three never. But only (a) is actually competing for that slot. (b) wants a ramp, which a glyph is bad at and a rule under a number is good at. (c) wants to move a card, which no glyph can do. Each one lands where its own shape already fits, and none of them crowds the others.

(b) Cache warmth parked 2026-10-09 kept as groundwork, not as a proposal

Withdrawn, and for a better reason than the ones I was weighing. I was arguing about accuracy — the turn-start gap, inferring the TTL. The actual objection is that a visible countdown is a deadline, and a rail full of draining rules would have you racing a timer to get a reply in. That is a worse rail even when the number is perfectly correct, so none of the accuracy work would have saved it.

Everything below stays, because the findings outlive the proposal: the cache numbers are already recorded end to end, only claude-code reports them, the clock starts at the request's start, and the TTL can be inferred from gaps we already observe. That is the factual base for the real question — what mads can do to cut token cost — where the useful moves act on the cache (keep-alives, prefix stability, when to compact) rather than narrating it at you.

What is actually available

mads already records the cache numbers, end to end. Usage carries CacheCreationInputTokens and CacheReadInputTokens (pkg/contracts/transcript.go:84-85), the claude-code provider fills them from the wire (providers/claudecode/wire.go:104-105), they are persisted on Session.LastUsage by the same write that stamps LastTurnAt (services/data/internal/store/sessions.go:246-266), and the UI type already exposes them (ui/src/router/types.ts:501-502). Nothing new has to be collected.

But only for claude-code. The ACP path reports input and output tokens only (providers/acprpc/session.go:511), and no cache fields exist on the goose or kiro paths at all. So warmth must degrade to silence on those harnesses — no rule under the stamp — and never to a false “cold”.

What the cache actually does Anthropic prompt-caching reference
FactConsequence for this design
Default ephemeral TTL is 5 minutes; ttl: "1h" is opt-in and doubles the write cost (2× vs 1.25×). mads does not set this — the harness does. So the TTL has to be observed, not configured. See the inference table below.
A cache read refreshes the timer, free, on either TTL. This is what makes the whole feature one subtraction: warmth is just time since the last turn. No bookkeeping, no state machine.
The lifetime is measured from the START of the request, and generation time counts against it — a 4-minute turn leaves about 1 minute of a 5-minute entry. The gap. See below.
Cache reads cost ~0.1× base input (0.05× on Opus 5.5); a miss re-reads the whole prefix at full price. Sets the stakes: being wrong costs one pricier, slower turn. Nobody loses work — which is exactly what licenses a heuristic here.
The one real gap a one-field server change

The cache clock starts when the request starts. mads only persists when the turn ended — RecordSessionTurnEnd stamps LastTurnAt (pkg/dataclient/dataclient.go:274). The turn's start does exist while the turn runs — AgentState.Since is documented as “the turn's start for every working event in it” — but the very next line says “Turn-end time on idle” (pkg/contracts/conversation.go:148-153), so it is overwritten the moment the turn finishes and the start instant is discarded.

On a 1-hour TTL the error is noise. On the 5-minute default it is decisive: counting from the wrong end of a 4-minute turn is the difference between “warm” and “expired”. The fix is one persisted field — last_turn_started_at, written by the same call that already writes the other two.

Inferring the TTL from turns we already have

Every turn gives us a free measurement: the gap since the previous turn, and whether this turn read from cache. We never have to ask the harness.

Gap since previous turncache_read_input_tokensWhat it proves
under 5 min> 0Nothing — consistent with either TTL. The common case.
5 min – 1 hour> 0Proof of the 1-hour TTL. The entry outlived 5 minutes, so the harness asked for the long one.
over 5 min0Evidence of the 5-minute default. Not proof — the prefix may have changed for another reason.
anyfield absentNot a claude-code session. Show no warmth at all.

So: assume 5 minutes, and let one long-gap cache hit upgrade the session to an hour. The display becomes evidence-based rather than configured, and it self-corrects for free if Claude Code ever changes its policy — which, since mads does not control it, it eventually will.

The goose card at the bottom is the point. No rule, no clause — not a cold one. We do not know, so we do not say.

Where I'd push back on your mapping. You proposed warm/cold as the difference between Done and Sleeping. I'd keep them separate, because Done is about you and warmth is about cost, and they genuinely come apart: a session can have finished its turn while you were away and gone cold (Done, cold — still your turn), or be warm from a turn you already read (Idle, warm — nothing waiting). Folding them would make the card wrong in both directions. So done keeps meaning what it means today — a turn ended and you haven't looked — and warmth runs underneath as its own quiet channel.

But your instinct kills “Sleeping” anyway, from the other side. “Ready” vs “Sleeping” was the process axis — and that's the axis you just described as unlocking a car door by hand. Both become Idle, and the question they were badly answering (“how expensive is it to pick this up again?”) is answered properly by the warmth clause instead. One word out, one real fact in.

Where it goes

Its own fold, above Earlier. I went back and forth and landed here: one fold with two doors would be tidier, but the two tails mean different things to you — I decided this versus time decided this — and only one of them is a list you'd ever scan deliberately. Both collapsed, so the cost is one 22px row.

What brings it back

It comes back on its own the moment it needs you — a parked approval, a crash, a stall. You said “until I need it again”; implementing that as until it needs you is both closer to what you want and the thing that makes the gesture safe to use. If setting aside could ever hide an alert, you'd stop trusting it within a week, and then it would be worse than not having it.

Everything else keeps it folded: finishing a turn does not un-set-aside a session. That's the difference between a notification and a task list.

On the icon: ✓ is the obvious task-list gesture and I did not use it — ✓ already means “the agent finished” two lines below, and one rail cannot have a checkmark meaning both it is done and I am done. ⌄ reads as “tuck this down there” and points at the fold it lands in. Open to alternatives — it's the weakest part of this page.

Where the flag lives

Server-side, not localStorage. railUnseen.ts keeps the unseen set in the browser, which is right for a view preference — but your task list should survive a browser, a machine and a reload. Session.tags already carries this kind of fact (retro, imported), so a tag is the cheapest honest home.

What parking (b) costs here

This block used to argue that setting a session aside is the gesture that frees its process — you don't lock the car, you walk away and it locks itself — guarded by only once the session has gone cold, so the sleep could never cost you a warm cache. Parking (b) removes the guard, so the argument goes with it.

The honest consequence: Set aside does not touch the process. It is a list operation and nothing else. That is a smaller feature than the one this page proposed yesterday, and it is the right size — the alternative is killing a harness on a timer we have just decided not to measure. ⏸ now stands or falls on pass 4's own argument (a latency optimisation with no other user-visible effect), not on this one.

(d) Done, without the checkmark pick one ✓ now belongs to Set aside

Giving ✓ to Set aside is the right trade — it is the gesture everyone already has for “I'm done with this”, and the rail gains something by the swap: ✓ comes to mean exactly one thing, and it is a thing you do. Every other mark on the card reports what the session is doing. Reserving the checkmark for the one control that records your judgement is a cleaner division than the one it replaces.

What the Done mark actually has to say. Worth being precise, because it is not “completion”: state.done is documented as “sticky: a turn ended and the session hasn't been opened since”, and it clears when you open the card. That is not a finished task — it is an unread flag, and the label already says so (“Done · your turn”). The mark should mean there is a reply in here you haven't read, which opens up better options than hunting for another checkmark.
