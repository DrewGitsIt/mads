Session worktrees: Commit and Land

Companion to docs/SESSION-WORKTREES-DESIGN.md. A session in a git repo works on its own branch in its own folder, and the user never sees the word "worktree". Two click-only verbs decide what happens to the work: Commit saves this session's files, and Land moves an isolated session's commits into the branch it came from.

2 · Commit dialog D5only files this session changed

Commit this session's changes
on mads/session/ses_86fc · as Drew

The list is the session's file-change ledger, not git status and not other sessions. Everything is checked by default. Clicking a path opens its diff, the same view as the Files tab.

Identity: the user's own git config. If git can't commit as you (no user.name, signing needs a passphrase), the card shows git's error. It never falls back to the mads-session identity. The commit carries a Session: trailer for people reading the log, and Commit records the hash itself rather than relying on the hook.

"Draft with Fast Model" fills the box from the checked files' diff. It's hidden when no Fast Model is configured.

Server-side, only paths in the session's change list are accepted, resolved with symlinks followed, and they must stay inside the session's folder. A file a pipeline already committed is reported as "already committed", not as a failure. Whole files only, no hunk staging (v1).

Known gap: files created only as a side effect of a shell command may not be in the ledger. Accepted for v1.

Undo appears only on a commit the Fast Model made without the dialog ("Write commit messages for me"), and only while it's still the branch tip. It's a reset --soft, so the files go back to uncommitted.

After Land the folder stays. The session branch tries to fast-forward to the base's new tip, so the next message continues on top of the landed work. That step is best-effort: the branch is already 0 ahead after a --no-ff land. Land records the merge commit's hash itself, because git merge doesn't fire the post-commit hook.

4 · When Land can't finish D6a conflict never touches your checkout

main moved on: 2 files conflict 14:05
scripts/deploy.sh, .github/workflows/deploy.yml changed on main too. Nothing was merged, and your checkout is untouched.
Bring in main and resolve the conflicts in scripts/deploy.sh and .github/workflows/deploy.yml, keeping both changes. Then commit.
Merged main into this branch. Kept the new runner matrix from main and our codename check…
Can't land while the agent is working 14:08
Land waits for the current turn to finish (or the running pipeline). Nothing changed.
Your checkout has uncommitted changes 14:11
Landing would overwrite scripts/deploy.sh in ~/repo/mads. Commit or stash it there, then Land again.

Before anything runs, Land refuses while the agent is mid-turn, a pipeline is running, the folder is mid-merge, or the folder isn't completely clean. User messages queue behind a running Land.

Step 1, in the session folder: merge main into the session branch. A conflict aborts there, and "Ask the agent to resolve" sends the message shown: an ordinary user turn the user can read and edit.

Step 2, in your checkout: first re-check the base. If it moved since step 1, go back to step 1. Then git merge --no-ff mads/session/<id>. It can't conflict, but it can be refused: your uncommitted edits to the same files, untracked files the branch would add, a merge hook, an in-progress rebase. Any failure runs merge --abort, so your checkout is never left mid-merge, and the card gives the reason.

If main isn't checked out in ~/repo/mads, the card says so. v1 doesn't land into a branch nobody has checked out.

The conversation, its tasks and this session's folder go too. The agent is stopped first. This can't be undone.

Close asks only when there's unlanded work, and never discards anything. Delete removes the folder and the branch. It warns in words, and there's no "keep the branch" option: keeping work is what Land and Keep for later are for. The delete panel extends session-delete-confirm.html's state panel.
