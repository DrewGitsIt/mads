Session rail — status legibility (v2)

Three asks, one surface: ui/src/features/sessions/rail/SessionRail.tsx + railGroups.ts. Card chrome itself was settled in docs/mockups/sessions-ux.html (Option A, quiet card) and is left alone here — everything below adds information, not controls.

  • #1 A live status line under the name, so "the agent is working" is visible at a glance.
  • #2 Something better than Active / Recent, which groups by "a child process exists".
  • #3 Datetime initiated and datetime of last response.

The last section is the one to read before estimating: part of #1 needs a small backend signal, the rest of all three is frontend-only with data the rail already has.

#1 Status line a second line under the name: spinner + what the agent is doing + elapsed

The problem today: a card carries a name, a dot, open-work chips, and (paused only) a summary teaser. The dot is dotState() — green whenever session.activity === "active", which means "a provider child process is alive", not "the agent is doing something". A session that has been sitting at an empty prompt for an hour and a session eight tool calls deep into a turn render identically. The only place "working" is visible is inside the open conversation (WorkingIndicator), i.e. for exactly one session at a time.

State vocabulary

Precedence top to bottom: the first state that applies wins, so an approval park always beats "working" and a crash always beats everything.

Accessibility / motion: the status line is the card's role="status" region, so a state change is announced once rather than the name being re-read; the spinner is decorative (aria-hidden) and under prefers-reduced-motion degrades to a static accent ring — colour and text carry the state on their own, matching WorkingIndicator's existing treatment. "Done · your turn" is a sticky state, not a flash: it holds until the session is opened or the next turn starts, which is what makes the rail usable as a "what came back while I was away" list.

Why a line and not just a colour: the same ask ("is it still going?") was already answered inside the conversation pane by giving the indicator an elapsed counter and an activity ticker rather than a busier dot — see ui/src/conversation/ChatRenderer/WorkingIndicator.tsx. The rail line is that component's one-line sibling and should reuse its vocabulary (toolTitle()) verbatim so the two surfaces never disagree.

#2 Grouping, filtering & labels Active / Recent means "a process exists" — useless in chat mode

The problem today: groupSessions() splits on activity === "active" and sorts each half by updated_at. With a live PTY that split is meaningful — a stream is either attached or it isn't. In chat mode it is an implementation detail: the child process is spun up and torn down by lifecycle rules the user never sees, a "Recent" session wakes transparently on the next send, and an "Active" session may have done nothing for an hour. Meanwhile the sort is right (recency), and none of the labels the rail could show — workspace, cwd, worktree branch, agent/persona, model — are shown at all. Three ways out, all keeping recency sort:

Option A · Attention buckets
Replace the two groups with three that answer "who needs me": Needs you (approval parked, crashed, blocked work), Working (turn in flight), Idle (everything else, live or sleeping, recency-sorted). Empty groups don't render. Status line does the per-card detail.

Lean: B — and the reason is the stability constraint below, not the chrome. Either way "Active / Recent" stops being the vocabulary; if a two-way split survives at all it should read Live / Sleeping, which is what it has always actually meant.

#2b Omni search one field instead of a workspace picker — try it, it really searches

A picker can only express the axis it was built for, and it costs a permanent control in a 280px rail to express it. A single field matches whatever you happen to remember — the session's name, the workspace, the directory, the branch — and disappears into a placeholder when you're not using it.

One correction to the premise, because it changes the field list: a workspace's name is not derived from its directory. It's a free-text field in WorkspaceEditor.tsx (the only validation is non-empty), and a workspace holds a list of repos with one marked primary — so it may have several directories, or a name like "Client work" that matches none of them. Convention makes name ≈ repo basename most of the time, but search can't rely on it. So the matcher indexes four fields per session — name, workspace, cwd, worktree_branch — and typing mads finds the session whether the workspace is called "mads" or "Main work". All four are already on the record the rail holds; this is a pure client-side filter, no endpoint.

#2c The stability contract "I don't want it to rise into Active and then fall out of sight"

This is the constraint that decides #2, so it's worth stating as a rule rather than leaving it implicit in an option. There are two separate forces that move a card, and only one of them is legitimate:

ForceMoves a card because…Verdict
live statethe agent started a turn / parked on an approval / finished — i.e. the card changed groupnever allowed to move a card — it may only repaint it
recencyyou or the agent actually did something in that sessionallowed, but deferred — and it only ever promotes

Three rules: (1) Status paints, never sorts. Working / needs-you / done change the line, the dot and the tone in place — never the index. (2) Order is settled, not live. The rail renders from an order snapshot; a new ordering is computed but only applied at a quiet boundary — pointer leaves the rail, rail loses focus, or you change the search/filter. A pending re-settle shows as a one-line ghost ("2 sessions moved ↑") you can click, Gmail-style, rather than yanking rows out from under the cursor. (3) The open session never moves, full stop — even a settle leaves the selected card's index alone until you select something else.

Scenario: a normal-looking rail — two sessions parked on approvals, one mid-turn, three idle. You open retro: conversation UX — last touched three weeks ago, bottom of the list (dashed outline) — and send it a message. Watch that one card in both panels. Red flash = it moved on its own; green = a settle you invited.

Grouped by state (option A / C's pin) 0 moves
Flat + settled order (option B) 0 moves

What the panels show: grouped, the card you are reading relocates twice for reasons you didn't initiate — up into Working the moment your message lands, then back down under the approval-parked and still-working sessions when the turn ends. That second move is exactly the "falls out of sight" failure, and it gets worse the busier the rail is: the drop is as deep as the groups above it are tall. Flat + settled, it moves once, to the top, and only after you've taken the pointer off the rail — and if it were the selected session, rule 3 would hold it even then, until you selected away.

Implementation note: this is a useRef holding orderedIds plus a pendingOrder, recomputed on the session list changing and applied on mouseleave/blur/filter change. Sessions that are genuinely new (or newly matched by a search) splice in at their sorted position immediately — appearing isn't moving, and nothing above them shifts by more than one row. Deleted sessions leave immediately too. It's maybe 30 lines in SessionRail, and it's worth writing once because every future "surface X in the rail" idea will otherwise re-introduce the jumping.

#3 Initiated & last response both timestamps exist on the record today

created_at is exactly "datetime initiated". "Datetime of last response" is approximately updated_at: the runner persists last_usage on every turn end, which bumps it — but so does a rename, a summary write, or an activity flip, so it drifts from "last reply" in ways a user will notice ("last reply 4s ago" on a session that only got auto-titled). Formatting rules (one helper, shared with the rest of the app): <60s → "now"; <60m → "14m"; today → "13:02"; this week → "Fri 09:14"; older → "24 Sep". Absolute ISO-ish in the title so it's always recoverable. Relative labels re-render on a single shared 30s tick, not one timer per card.

The honest fix: add last_turn_at to the session record, stamped where the runner already persists last_usage on turn end (services/session/internal/runner/runner.go's persistUsage). It's a couple of lines, it makes "last response" mean what it says, and it gives the rail a correct sort key that a rename can't perturb. Until then updated_at is a fair v1 as long as the label reads "last activity", not "last reply".

wiring What the rail can know today read this before estimating #1

The rail is one component watching all sessions, so every signal it uses must ride the shared control-plane stream. ui/src/router/events.ts multiplexes one EventSource for the whole window and filters server-side by type only — which is perfect here (a new type costs nothing, and no reconnect on session switch). The per-session data-plane /output stream is the opposite: one connection each, and the ~6-socket-per-origin cap is exactly why the rail must never open one per card (see that file's own comment). That single fact decides the phasing.

Rail wantsControl-plane todayVerdict

thinkingsession.thinking — whole blocks, appended after the block; token ticks are deliberately live-onlylaggy

subagents runningsession.subagent_task, every phase incl. progresshave

blocked workuseOpenTaskCounts() already feeds the railhave
timestampscreated_at exact; updated_at ≈ last turn end (plus rename/summary noise)good enough

The missing piece is small and already exists in-process. Runner.busy (services/session/internal/runner/runner.go) is the authoritative "a turn is in flight" flag — set on Send, cleared in onTurnEnd. It simply never leaves the session process. Proposal:

  • New event session.agent_state, payload {state, label, since} — state from the enum above, label built by the same enrichment that already produces ToolUse.title (so the rail line and WorkingIndicator's ticker can't disagree). Emitted on transitions only, coalesced (~500ms floor) so a tool-heavy turn doesn't spam the log — and skipped for parent-tagged subagent events, which roll up as a count instead.
  • Mirror the latest onto the session record (agent_state + last_turn_at) so a cold page load and an SSE reconnect render correctly from GET /sessions without replaying events. Without the mirror, a refresh mid-turn shows every card idle.
  • Frontend: useSessionAgentState() alongside useOpenTaskCounts() (same shape — one map keyed by session id), plus statusOf(session, agentState, breakdown) in railGroups.ts next to dotState(). SessionRail renders one new <div class=status>; no change to its props contract beyond the new map.
